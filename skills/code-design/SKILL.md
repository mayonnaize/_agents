# Code Design

要件、利用者から見た動作、コードの責務を対応付け、実装とレビューに使える設計書を作成する。

## 1. 対象と根拠を確認する

1. ユーザーが指定した対象機能、作成・更新する文書、変更範囲を確認する。
2. 対象リポジトリの作業ルール、既存の要件・設計書、関連ソースとテストを読む。既存実装では入口から呼出先、データ、状態、外部連携まで対象操作を追う。
3. 現行の動作と今回の要求を分け、参照した資料・ソースのパスと該当箇所を記録する。追加変更では基準となるリビジョンも記録する。
4. 要求と現行実装が異なる場合は、その差を明記する。新規設計の提案は提案と明記し、確認済みの仕様として扱わない。
5. 設計を左右する未確定事項は、具体的な質問、確認先、影響する設計箇所として確認事項に記録する。その判断に依存する設計・実装は進めず、確定している範囲を記述する。資料で解決できず進行不能な事項だけユーザーに質問する。

## 2. 作成する文書を選ぶ

依頼された文書に対応するテンプレートを読み、必要な文書だけを作成する。3種類を一律に生成しない。既存の上位文書がある場合は参照し、書き直さない。

| 文書 | 記述する範囲 | 読み込むテンプレート | 既定の出力先 |
| --- | --- | --- | --- |
| 全体設計書 | システムの構成、実行単位、全体の動作、状態管理、停止・復旧の分担、通信の概要 | [overall_design_template.md](references/overall_design_template.md) | `spec/overall-design.md` |
| 機能仕様書 | 操作と観測できる動作、受付条件、入出力、外部IF、機能の状態と異常時の動作 | [functional_spec_template.md](references/functional_spec_template.md) | `spec/<機能名>/functional-spec.md` |
| コード設計書 | クラスや関数の責務、配置、公開操作の契約、処理順序、データ、状態の所有者 | [code_design_template.md](references/code_design_template.md) | `spec/<機能名>/code-design.md` |

ユーザーの指定と対象プロジェクトの既存の配置・命名規則を既定の出力先より優先する。レビュー依頼では文書を勝手に変更せず、根拠と該当箇所を伴う指摘を返す。

## 3. テンプレートを対象に合わせて具体化する

- テンプレートの章構成と粒度を基準にし、説明用の角括弧、仮名、記入指示を実際の名称と動作に置き換える。該当しない節は削除し、番号と参照先を合わせる。
- テンプレートの構成例を要件として採用しない。実際に存在する、または要求から必要と判断できる実行単位、状態、操作だけを記載する。単一プロセスにワーカーを足したり、状態を持たない関数に状態遷移を作ったりしない。
- コード設計では公開メソッド・関数の入力と制約、処理順序と分岐条件、更新内容、戻り値、仕様上必要な失敗時の処理を具体化する。関数主体のコードではクラスを新設せず、モジュールと関数で同じ情報を表す。
- 既存の命名、依存関係、責務分担を調べて使う。設計書を埋めるための抽象化、互換層、再試行、例外処理、同時実行対応を追加しない。必要性が確認できたものだけを定義する。
- 図は指定がなければMermaidを使用する。構成図は配置と境界、クラス図は責務と関係、シーケンス図は連携順序、状態図は成立する事実と操作条件を示す。説明する関係がない図は省く。
- 状態を扱う場合は管理対象と所有者を特定し、状態の定義、受付可能な操作、遷移の契機と成立条件を対応させる。単に「待機」「実行中」と名付けて済ませない。
- 追加・変更では基準から変わる文章、表の項目、操作、矢印ラベルに★を付け、図の変更ノードや区間をオレンジで示す。新規設計の全要素に変更マークを付けない。
- 同じ定義を複数文書へ複製せず、定義元の節へ相対リンクする。未作成の文書は存在する参照先として扱わず、確認事項に記録する。
- 要件やコードを引用する場合は確認できた箇所だけを示す。存在しないクラス、ファイル、API、テスト結果を根拠として書かない。

## 4. 整合性を確認する

保存前に、作成・更新した範囲について次を照合して修正する。

- **操作とコード**：操作の契機、受付条件、入力、結果が、公開メソッド・関数と処理シーケンスに対応しているか。
- **状態と異常**：同じ状態名・条件を使い、成功・拒否・失敗の結果と状態更新が矛盾していないか。停止・復旧は対象の要件にある範囲で対応しているか。
- **データとIF**：送受信者、IF名、データ項目、型、単位、制約が本文・表・図で一致しているか。
- **図と参照**：Mermaidの構文、図中の名称、ファイルへのリンクと節番号が正しいか。利用可能なMermaid検証手段があれば構文を検証する。実行していない検証を実施済みと書かない。
- **根拠と範囲**：現行仕様、変更要求、提案、未確定事項を区別できるか。変更マークが今回の差分だけを示しているか。
- **完成度**：記入指示やサンプルの仮名が残っていないか。埋められない仕様は推測で補わず、確認事項へ移したか。

文書を保存し、作成・更新したファイルと、設計に影響する未確定事項だけを簡潔に報告する。設計依頼から実装へ自動で進まない。
