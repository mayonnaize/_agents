# Code Design

要望と根拠を整理し、構成・動作・実装構造を順に設計する。実装担当が主要な仕様を追加判断せずに実装できる具体性を目指す。

## 成果物

| 文書 | 標準出力先 | 担当する内容 | テンプレート |
| --- | --- | --- | --- |
| 全体設計書 | `docs/design/全体設計書.md` | 目的、システム境界、構成要素、連携、全体の状態と運用 | [全体設計](references/overall_design_template.md) |
| 機能仕様書 | `docs/design/features/<機能名>/機能仕様書.md` | 利用者や連携先から見た操作、入出力、状態、異常時の動作 | [機能仕様](references/functional_spec_template.md) |
| コード設計書 | `docs/design/features/<機能名>/コード設計書.md` | ファイルと責務、関数やクラスの契約、処理の順序、状態の所有者 | [コード設計](references/code_design_template.md) |

出力先は明示指定、既存文書の配置、標準出力先の順で選ぶ。文書名は日本語を標準とする。機能名は対象の呼称に合わせる。

## サブコマンド

依頼の先頭のサブコマンドから担当する作業を選ぶ。対象、今回の要求、根拠となる文書やコードを後ろに続ける。自然文で特定の作業を依頼された場合も同じ単位で扱う。

| 呼出し | 作業と参照する工程 | 成果物と終了条件 |
| --- | --- | --- |
| `/code-design scope [対象]` | 工程1・2で調査、要件整理、変更の影響範囲を特定 | 全体設計書の「目的・範囲」「設計判断と前提」「確認事項」に要件、根拠、前提、未決事項を保存して終了 |
| `/code-design overview [対象]` | 工程1・2の根拠を確認し、工程3で全体を設計 | 全体設計書を作成・更新し、全体の利用場面と構成要素の分担を検証して終了 |
| `/code-design feature <機能名>` | 関連する全体設計と根拠を確認し、工程4で機能を設計 | 対象の機能仕様書を作成・更新し、操作、入出力、状態、異常・復旧を検証して終了 |
| `/code-design code <機能名>` | 関連する全体設計・機能仕様と実装を確認し、工程5で実装構造を設計 | 対象のコード設計書を作成・更新し、公開操作と処理順序を機能の契約に照合して終了 |
| `/code-design review [対象]` | 工程6で対象の設計を関連文書・要件・コードと照合 | 問題箇所、不成立となる具体例、影響、修正方針を報告して終了 |

### 共通の入力と再開

- 対象はシステム、機能名、文書パスで指定する。省略時は依頼内容、既存の文書構成、直前の合意から特定する。複数候補で作業範囲が変わる場合は一問で確認する
- 今回の要求と根拠は自然文やパスで受け取る。前回の要件・採用理由・未決事項を読み、現在の依頼とコードとの差分に沿って追加調査する
- 単独実行で上位文書が存在しない場合は、必要な契約と前提を対象文書に定義する。影響の大きい判断には工程2の確認基準を適用する
- 各設計コマンドで工程6・7の該当範囲を確認し、指定された作業を完了する。段階の完了報告には、成果物、主な判断、残る確認事項を記載する

`scope`で全体設計書を新規作成する場合は、要件整理の範囲であることを示し、整理できた節を保存する。既存文書では対応する節へ要件と判断を追記し、構成や動作の再設計は`overview`へ引き継ぐ。

### 既存設計の更新

`overview`・`feature`・`code`は、対象文書と変更要求から更新も担当する。変更する契約、その定義元、参照する文書と呼出元への影響を確認する。対象文書を更新し、関連文書への影響と必要な修正を報告する。関連文書の更新まで依頼された場合は、対応する設計作業を続けて実施する。

`review`の成果物は診断結果とする。各指摘に文書の節やコードのシンボル、問題が起こる入力・操作、期待結果との差、影響と修正方針を添える。修正依頼は対象に対応する設計コマンドで扱う。保存先の指定があれば、その場所にレビュー結果を保存する。

### サブコマンド無指定の進行

要件整理 → 全体設計 → 機能仕様 → コード設計の順に進め、各段階の設計案と判断理由を提示して確認を得る。一括作成の指定があれば連続して作成する。各段階で保存した根拠と判断を次へ引き継ぐ。

## 1. 要望と現状を調べる

依頼から、利用者、達成したい結果、対象機能、今回の変更範囲、制約を整理する。曖昧な要望は具体的な操作と結果に言い換える。

既存システムでは、リポジトリの作業規約、関連仕様、呼出元から保存先までの実装、設定、テストを対象機能に沿って読む。要件との関係が分かるファイルパスとシンボルを控える。新規開発では、提供資料と連携先の契約を根拠にする。

現状、実現したい動作、差分を整理する。現状の実装と要望が食い違う箇所は、具体的な操作例と影響を示して設計判断につなげる。

## 2. 要件と判断を固める

要件ごとに、契機、前提、入力、完了時の結果、制約を整理する。性能、権限、保存期間、利用環境などは、対象の使い方に関係するものを確認する。

### 判断の進め方

- 既存の慣習と要件を根拠に、命名、配置、内部の責務分担、処理方式の推奨案を決めて進める。設計に影響する前提と採用理由を記録する
- 目的、対象範囲、費用、権限、データの削除など、誤った判断の影響が大きい事項はユーザーに確認する。質問は一問ずつ、推奨案と理由を添える
- 判断が分かれる方式は、対象要件に関係する利点、負担、影響範囲を比較して推奨案を選ぶ。確認は判断の影響に応じて行う
- 回答待ちの事項は、必要な情報、影響箇所、確認先を記録する。独立して設計できる箇所は進める

既存構成の再利用で要件を満たせるか確かめる。見直しが必要なら、具体的な問題、変更理由、影響範囲、移行方法を示して確認する。

## 3. 全体を設計する

全体設計テンプレートを読み、システム境界と実行単位を決める。構成要素の責務、データの管理元と受渡し先、通信、起動と終了を対応付ける。

利用者の開始操作から結果の確認までをたどり、同期応答と非同期通知、受付と処理完了を区別する。複数の構成要素にまたがる状態、停止順序、復旧の判断主体を決める。

対象機能を一覧にし、各機能が担当する範囲と文書の参照先を示す。

## 4. 機能の動作を設計する

機能仕様テンプレートを読み、操作や自動処理ごとに受付条件、入力、処理、完了条件、表示・通知・保存する結果を定義する。

状態ごとの操作可否、同じ要求の繰返し、同時要求、途中の中止と再実行を、対象の利用場面に合わせて決める。異常は検出条件、処理、通知、状態とデータの扱い、復旧操作までつなげる。

入出力と外部IFの契約はこの文書を定義元とする。項目の型、意味、制約、成功と失敗の判定、対象に必要な認証・時間制限・再試行を具体化する。

## 5. 実装構造を設計する

コード設計テンプレートを読み、機能の動作を実装単位に割り当てる。既存コードの再利用先と変更先を特定し、各ファイルの責務と依存の向きを決める。新設する構造は、満たす要件と役割を説明する。

対象の言語とコードベースに合わせてクラス、関数、モジュールで表現する。公開関数やメソッドごとに、入力と戻り値、受付条件、処理順序と分岐、更新内容、失敗時の通知と後始末を記載する。局所的な変数名や自明な処理は実装担当の裁量とする。

状態とデータの所有者、非同期処理の完了判定、並行操作の制御、保存や外部通信の失敗時の整合を、担当する実装単位と結び付ける。複数の実装単位が連携する場合は、呼出順序と受け渡すデータを示す。

機能仕様の契約を参照し、ここでは外部形式と内部の型の対応、処理を担当する関数、保存・更新の方法を定義する。

## 6. 利用場面で設計を検証する

正常な操作を開始から完了までたどる。入力不備、繰返し操作、同時実行、途中失敗、中止、復旧から、対象に該当する場面を選んで同様にたどる。

各場面で、判断主体、受付可否、呼出先、状態とデータの更新、利用者に届く結果を確認する。設計の作成・更新では、不足や矛盾を対象範囲で解消し、関連文書への影響を示す。`review`では、問題の根拠と具体例を修正方針にまとめる。

| 確認対象 | 確認する対応 |
| --- | --- |
| 要件 | 担当する構成要素、具体的な動作、検証する操作と期待結果 |
| 操作と状態 | 受付条件、遷移の契機、更新内容、完了表示 |
| インターフェース | 呼出側と提供側のデータ、応答、失敗時の扱い |
| 実装構造 | ファイル、関数、依存関係、状態とデータの所有者 |
| 文書間 | 全体の機能分担、機能の契約、コード上の担当と呼出順序 |

不確かな性能や外部連携など、実現性に疑問が残る箇所は、検証する仮説、試作や計測の方法、合否の基準を提案する。実行はユーザーの依頼範囲に合わせる。

## 7. 設計書を仕上げる

要件と設計箇所、具体的な入力・操作・期待結果を対応付けて検証観点を記録する。未決事項には影響箇所と確認先を添える。主要な動作を左右する回答待ちがあれば、設計の確定に必要な事項として提示する。

現状の根拠として参照した資料、ソースのパスとシンボル、対象リビジョンを記録する。設計上の検証結果と、試作・テストを実行した結果を区別して報告する。

### 記述と図の扱い

- テンプレートは対象に合わせて節を選び、具体的な名称と動作で埋める。未使用の節と案内文は仕上げ時に除く
- 図はMermaidを標準とする。構成、連携、状態、データの関係から、設計判断を伝えるものを選ぶ
- 既存改修では、基準となる仕様やリビジョンを示し、追加・変更部分をオレンジ色と`★`で示す。新規開発では通常表記で全体を記述する
- 詳細の定義元を一つに定め、他の文書や図は参照で結ぶ。図のラベルは関係と処理の要点、詳しい条件や手順は対応する本文に記載する
- 文は主体、動作、条件、結果を具体的に書く。選択理由には対象要件と比較した負担や効果を添える

最終報告は、作成・更新した文書、主な設計判断、検証した範囲、残る確認事項を簡潔に示す。
