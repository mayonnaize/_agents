# Create Architecture Spec

このスキルは、プロジェクトのアーキテクチャ仕様書を、一貫した粒度と高品質なフォーマットで作成するためのガイドラインである。

## 重要な基本ルール
- **出力先とファイル名**: 特に指定がない限り、プロジェクトルートの `spec/` ディレクトリ内に `architecture.md` （または対象機能に応じた `[機能名].md`）として出力すること。ディレクトリ名（`spec/`）とファイル名のプレフィックス（`spec-`）が重複するような冗長な命名は避けること。
- 出力はMarkdown形式で行うこと。
- UML作成時は、指定がない限り必ず**Mermaid**を使用すること。
- 推測で仕様を定義しないこと。仕様が不明な点はドキュメント化を止めてユーザーに質問すること。

## Workflow

仕様書を作成する前に、推測による仕様定義を防ぐため、必ず以下の手順でコードベースの実態調査を行ってください。

1. **Phase 1: 実態の調査**
   対象プロジェクトのディレクトリ構成や使用技術、依存関係を正確に把握するため、同梱の `scan.py` を実行してください。
   ```bash
   python3 "$SKILL_ROOT/scripts/scan.py" --output .scratch/.codebase-scan.txt
   ```
   ※ `$SKILL_ROOT` はこのスキルフォルダの絶対パスです。
   出力された `.scratch/.codebase-scan.txt` を読み込み、`references/inquiry-checkpoints.md` や `references/stack-detection.md` を活用して、プロジェクトの実際の構造、フレームワーク、主要なモジュールを調査してください。

2. **Phase 2: 仕様のドラフト作成**
   調査した事実ベースの情報と、ユーザーの要件をもとに、`references/template.md` に沿って仕様書のドラフトを作成します。
   コードから読み取れない意図や不明点がある場合は、勝手に推測せず、必ず `[ASK USER]` としてユーザーに質問を投げてください。

3. **Phase 3: 仕様書の出力**
   フィードバックを反映し、最終的な `spec/architecture.md` を出力します。

## 仕様書の基本構造
仕様書の基本構造と粒度については、必ず同梱の `references/template.md` を参照すること。
要件に応じて柔軟に変更可能だが、指定されたテンプレートの示す基本の粒度や構成は維持すること。

## 成果物の品質向上のポイント
- **図だけを置かない**: 図（Mermaid）の直後には必ず「補足」見出しを作成し、各要素の役割や「なぜその設計にしたのか」という設計意図をテキストで説明すること。
- **視認性**: Mermaid図の中で複雑な処理やまとまりがある場合は、`subgraph`（構成図）や `rect`（シーケンス図）を使ってグループ化すること。

## Bundled Assets

| Asset | When to load |
|-------|-------------|
| `scripts/scan.py` | Phase 1 — コードベースの実態を調査するために最初に実行するスクリプト |
| `references/inquiry-checkpoints.md` | Phase 1 — 調査すべき観点を確認するために参照する |
| `references/stack-detection.md` | Phase 1 — 使用技術が不明瞭な場合に、技術スタックを特定するために参照する |
| `references/template.md` | Phase 2 — 仕様書の基本構造と粒度を確認するために参照する |
