# Create Architecture Spec

コードと要件を根拠に、日本語のアーキテクチャ仕様書を作成する。事実、設計判断、仮定、未決事項を分け、読み手が根拠と判断理由を追える状態にする。

## 1. 依頼を分類する

### 設計モード

ユーザーの指定を優先する。指定がない場合は質問せず、次の順で自動判定し、成果物のメタデータにモードと判定理由を書く。

- **Gap**: 現行と目標、移行、置換、段階導入、差分のいずれかを扱う。
- **To-Be**: 新機能、変更後の構成、未実装システムを設計する。
- **As-Is**: 既存コードの構造や動作を記録する。

複数に該当する場合は Gap を選ぶ。As-Isの事実とTo-Beの判断を同じ記述に混ぜない。

### 成果物

ユーザーが「基本設計」「詳細設計」「両方」を指定した場合は従う。指定がなければ基本設計書だけを作る。

- 基本設計書: `spec/<対象slug>/basic-design.md`
- 詳細設計書: `spec/<対象slug>/detailed-design.md`

ユーザーが出力先を指定した場合は、その指定を優先する。既存ファイルを更新する場合は、対象と更新意図を確認してから変更する。出力言語は常に日本語とし、コード識別子、API名、規格名は原文を保つ。

## 2. 調査する

仕様書を書く前に、プロジェクトルートで次を実行する。

```bash
python3 <このスキルのディレクトリ>/scripts/scan.py --output /tmp/codebase-scan.txt
```

スキャン結果は調査対象を探す地図であり、仕様の根拠ではない。次の順で実物を読む。

1. `AGENTS.md`、`CLAUDE.md`、README、既存仕様、設定ファイル
2. 関連manifestとビルド・テスト設定
3. エントリポイントから対象処理の終了点までの呼出経路
4. データ定義、外部接続、認証・認可、永続化、失敗処理
5. 対象に関係するテストと履歴

調査観点は `references/inquiry-checkpoints.md` を使う。技術スタックが判別しにくい場合だけ `references/stack-detection.md` を読む。

As-IsまたはGapでは、コミットID、ブランチ、調査日時、未コミット変更の有無を記録する。未コミット変更を含めて調査した場合は、その事実を明記する。

## 3. 要件と根拠を整理する

本文を書く前に、内部メモとして要件と証拠を分類する。

| 種別 | ID | 内容 |
|---|---|---|
| 機能要件 | `FR-01` | システムが行うこと |
| 非機能要件 | `NFR-01` | 性能、可用性、セキュリティなど |
| 制約 | `CON-01` | 技術、運用、互換性、期限などの制約 |
| 根拠 | `E-01` | コード、設定、要件、利用者回答 |
| 設計判断 | `D-01` | 採用案と理由 |
| 仮定 | `A-01` | 確定前でも作業を続けられる前提 |
| 未決事項 | `Q-01` | 確認または決定が必要な事項 |

重要な事実には根拠IDを付ける。コード根拠には、ファイル、シンボル、必要なら行番号を記録する。行番号だけを根拠にしない。

### 不明点の扱い

次の不明点は後続設計を変えるため、文書作成を止めて依存順に1問ずつ確認する。各質問には推奨案と選択時の影響を添える。

- システム境界、データ所有者、信頼境界
- 認証・認可、個人情報・機密情報の扱い
- 互換性、移行、破壊的変更の許容範囲
- 主要技術の選定、責任分担、必須の品質目標

後続設計を変えない不明点は、`A-*` または `Q-*` として記録してドラフトを続ける。根拠のない数値、主体、原因、API、テーブルを作らない。

未決事項の担当者や決定者を、役割名で補ってはならない。「API所有者」「DB責任者」「セキュリティチーム」などが要件やリポジトリに存在しない場合、担当欄は `未定` とする。解決に必要な条件だけを記載し、架空の組織や外部サービスを作らない。

詳細設計では、不明点をすべて `Q-*` に移して実装契約を空白にしない。スコープ、データ所有、信頼境界、互換性、規範値を変えない範囲の構造的な振る舞いは、最小で可逆な案をDecision Logに記録して確定する。例えば、同一冪等キーの同一要求は初回結果を返す、異なる要求は状態を変更せず拒否する、競合時は一方だけを確定する、エラー本文は機械判定用コードと説明を持つ、といった契約が該当する。新しいHTTPステータス、保持期間、再試行回数などの数値は利用者確認なしに決めない。

要件にない既定値を「一般的」「安全」「実装可能」といった理由で補わない。文字数、件数、時間、回数、保持期間、閾値、列挙値、HTTPステータス、再試行間隔は、利用者または既存システムが示した値だけを規範として使う。別の要件にある数値を流用しない。値を決める材料がなければ `Q-*` とし、例示値を仕様値のように書かない。Decision Logだけを根拠に、未提示の数値を新規決定してはならない。

要件資料を1つの包括的な根拠IDへまとめない。要件の各項目に個別の `E-*` を付け、仕様中の値と規則を元の項目まで追跡できるようにする。

## 4. 設計書を書く

- 基本設計書は `references/basic-design-template.md` を使う。
- 詳細設計書は `references/detailed-design-template.md` を使う。
- 章を埋めるためだけに対象外のAPI、DB、キュー、インフラを作らない。
- 基本設計書には、Mermaidのシステム構成図と主要ユースケースのシーケンス図を必ず含める。
- ER図、状態遷移図、データフロー図、配置図は、文章より関係を理解しやすくなる場合に追加する。
- 各図の直後に、要素の役割、境界、設計理由を文章で説明する。
- Decision Logには、選択肢、採用理由、トレードオフ、影響、関連要件を記録する。

性能、可用性、セキュリティ、プライバシー、保守性、可観測性、運用性、互換性を毎回評価する。関連項目だけを仕様化し、非該当の場合は理由を残す。

詳細設計書では、該当する契約、データ、状態、処理規則、境界値、失敗、再試行、タイムアウト、冪等性、並行性、ロールバック、検証条件を確定する。実装者に設計判断を残さない一方、実装コードそのものは複製しない。

特に、冪等再送、同時実行の勝敗、重複要求、状態遷移、部分失敗、エラー本文の最小構造は未記入にしない。要件に直接書かれていなければ、数値を追加せずDecision Logで振る舞いを確定する。外部公開するステータス番号など、数値の選択が必要な部分だけを `Q-*` として分離する。

冪等処理では、認証と要求同一性の確認後、保存済みの完了結果を、変動する外部状態の再評価より先に返す。再送時に外部依存先の障害や状態変化が初回結果を覆さないようにする。処理中、同一キーで異なる要求、保存前失敗も個別に定義する。

詳細設計の各契約、データ制約、処理規則、失敗処理、検証条件には、対応する `FR-*`、`NFR-*`、`CON-*` または `D-*` を付ける。章末の一覧だけでは追跡可能とみなさない。

## 5. 日本語を推敲する

内容を確定した後、`references/writing-quality.md` と `references/yomiyasu-business.md` に従って全文の自然言語を推敲する。

コードブロック、Mermaid構文、JSON、パス、識別子、要件ID、根拠ID、引用値、契約値は変更しない。図中の説明ラベルを直す場合も、識別子と構文を保つ。

保存前に次を実行する。

```bash
python3 <スキルディレクトリ>/scripts/yomiyasu_lint.py <成果物>
python3 <スキルディレクトリ>/scripts/yomiyasu_diff.py <推敲前> <成果物> --stance=決まり
```

警告は修正候補として全件確認する。文脈上正しい専門用語や表現は、理由を内部の検査記録へ残して許容する。警告を消すためだけの書換えはしない。

保存前に成果物内の数値、時間単位、回数、長さ、割合、列挙値、HTTPステータスを検索する。それぞれについて、同じ対象・同じ意味の値が要件またはAs-Is根拠に存在することを確認する。存在しない値は削除するか `Q-*` に置き換える。メタデータの日時、章番号、IDの連番はこの監査対象外とする。

## 6. 出力前に検証する

`references/quality-gates.md` を使い、次を確認してから成果物を渡す。

- 重要な記述を要件、根拠、判断、仮定、未決事項のいずれかに分類できる。
- 要件ID、根拠ID、Decision Logの参照先が存在する。
- 推敲前後で、主張、条件、否定、数量、断定強度、責任主体が変わっていない。
- 保護対象とMarkdown構造が壊れていない。
- Mermaid図を解析できる。
- `[ASK USER]`、テンプレート説明、内部メモが成果物に残っていない。

検証できなかった項目は、完了したと表現せず、未実行の確認と理由を報告する。
